# Deployment Strategies: Every Deploy Is a Hypothesis, and Rollback Is the Escape Hatch You Must Test

**Applies to:** tool-agnostic; examples reference Kubernetes rollouts, Argo Rollouts / Flagger-class progressive delivery (verified 2026), and LB/service-mesh traffic shifting · **Last verified:** 2026-07-14

**The one-sentence philosophy:** a deployment strategy is not "how we copy bits to servers" — it is how much of production you're willing to bet on the hypothesis "this version works," how fast you find out you were wrong, and what it costs to take the bet back. Every strategy is a different answer to those three questions, and the right one is a function of blast tolerance and rollback cost, not fashion. The unforgivable version of this doc is the team that built a beautiful canary pipeline and has never once actually rolled anything back — an untested rollback path is a diagram, not a capability.

**Vocabulary this doc assumes:** *rolling update* — replace instances gradually in place; *blue-green* — full parallel environment, switch traffic at once; *canary* — small real-traffic slice on the new version, judged before proceeding; *bake time* — how long the canary must soak before judgment; *roll forward* — fix by shipping a new version instead of reverting.

## The decision tree

- **Rolling update (the default)** when: stateless-ish service, versions N and N+1 can coexist behind one endpoint, moderate blast tolerance. Cheapest, built into every orchestrator. Its blind spot: some pods are always mid-replacement, so "which version served this request" is ambiguous during the window, and a slow-burn defect can be fully rolled out before anyone judges it.
- **Canary** when: high traffic (enough for statistics — a 1% slice of 50 rps is noise), real user impact is the thing you fear, and you can measure "worse" quickly. The only strategy that *tests the hypothesis on real traffic before betting everything*. Costs: metric discipline, longer deploys, and version-coexistence just like rolling.
- **Blue-green** when: versions *cannot* coexist (breaking wire format, big-bang framework migration), or cutover+rollback must be near-instant and atomic, or a compliance gate demands a fully-verified idle environment before switch. Costs: 2× capacity during the window, and the database doesn't get a green copy — schema compatibility is still on you (below).
- **Recreate (stop-the-world)** when: singleton with an exclusive resource (lock, license, single-writer store) and a maintenance window is acceptable. Downtime by design; say so out loud.
- Orthogonal to all four: **feature flags** decouple *deploy* from *release* — ship dark, enable per-cohort, kill switch without a deploy. The flag system then becomes part of your delivery path: flag state must be versioned/auditable, and a flag that's been 100%-on for a quarter is dead code wearing a config knob.

Pick per-service, write the choice and its rollback procedure in the service's runbook, and revisit when traffic or coupling changes — a strategy chosen at 100 rps is often wrong at 10k rps.

## Failure modes

### 1. Canary analysis that doesn't catch regressions

- **Failure mode:** the canary "passes" and the regression ships anyway. The recurring causes: **wrong metrics** (judging on pod-health/CPU while the regression is user-facing — error rate, latency, correctness; a canary judged on "did it crash" approves every silently-wrong version); **no baseline comparison** (judging canary against a static threshold instead of against the *control* — the stable pods serving the same traffic at the same time; time-of-day effects swamp static thresholds); **too-short bake** (5-minute canary approves the memory leak that OOMs at hour three, the cache that poisons at TTL expiry, the cron-triggered path at midnight); **too-small sample** (1% of low traffic = a handful of requests; the p99 regression is statistically invisible); **unjudged dimensions** (canary healthy on HTTP metrics while writing corrupt rows — a canary that can corrupt shared data has bet the database, not 5% of traffic).
- **Detection:** the audit question with teeth: *when did a canary last fail?* A canary gate that has approved everything for six months is either guarding excellent engineering or judging nothing — check which by replaying a known-bad release in staging and confirming the analysis flunks it.
- **Fix:** judge canary-vs-control on the user-facing golden signals (error rate, latency percentiles, and one or two service-specific correctness metrics); bake time ≥ one full traffic/behavior cycle of the defect classes you fear (leak → hours; TTL → your TTL; batch job → its schedule); minimum-sample floor before judgment is allowed.
- **Prevention:** automated analysis (Argo Rollouts/Flagger-class) so judgment is a config artifact that gets reviewed, not a human glancing at a dashboard while eating lunch (mechanism); the known-bad replay drill quarterly (gate); metric *selection* reviewed by whoever owns the SLO — which metrics constitute "worse" is an SLO question, and `reliability-engineer/principles/slos-and-error-budgets.md` owns it.

### 2. Rollback automation that doesn't trigger — or can't

- **Failure mode:** three escalating versions. *Doesn't trigger:* auto-rollback watches the wrong signal (probe status, not error rate) or its threshold was set so wide it never fires — the bad version sits at 100% while a human notices from a customer report. *Can't roll back:* the previous artifact was garbage-collected from the registry, the rollback path needs a pipeline that's currently red, or rollback was never automated and the one person who knows the manual steps is asleep. *Rolls back into a wall:* the new version already wrote data the old version can't read — the rollback crashes harder than the bug it fled (see failure mode 4).
- **Detection:** measure **time-to-restore** in every deploy postmortem — decision-to-safe, minutes. And the standing drill: roll back a healthy service in prod, on purpose, quarterly. If that sentence frightens the team, the fear *is* the finding: rollback is your primary safety mechanism, and a safety mechanism you're afraid to test is one you don't have.
- **Fix:** rollback = redeploy of the previous *immutable artifact by digest* (`devops-engineer/topics/release-engineering.md`) through a path that does not depend on a full pipeline run — a red CI must never hold rollback hostage; keep N previous artifacts pinned against registry GC; one command or one button, documented in the runbook, executable by whoever is on call.
- **Prevention:** auto-rollback wired to the same canary/burn-rate analysis that gates promotion (mechanism); artifact-retention policy exempting the last N releases (mechanism); the quarterly rollback drill (gate); "what is the rollback and when did we last exercise it" as a mandatory line in every deploy-affecting design review (process).

### 3. Traffic-shifting bugs at blue-green cutover

- **Failure mode:** the switch is not as atomic as the diagram. Real incidents behind each clause: **DNS-based cutover** honoring TTLs means clients split across blue and green for minutes-to-hours (and some resolvers ignore TTL entirely); **long-lived connections** (websockets, gRPC streams, keep-alive pools) stay pinned to blue after "cutover," so blue's teardown kills them mid-flight; **in-flight state** (sessions, in-memory carts) on blue doesn't exist on green — users logged out or carts emptied at the moment of switch; **green never took real traffic** until 100% of it arrived at once — cold caches, unwarmed pools, first-request compilation: green buckles under full load it never rehearsed.
- **Detection:** during cutover, watch version-labeled request metrics on *both* colors — traffic draining from blue at the expected rate is the signal; blue still serving after cutover is the alarm. Synthetic checks pinned to each color independently.
- **Fix/prevention:** shift at the LB/mesh layer, not DNS, when you need atomicity (mechanism); connection-drain blue with a deadline (drain, don't kill); externalize session state so neither color owns it (`devops-engineer/topics/environment-parity.md` — state-in-the-instance is also an env-parity smell); warm green (traffic replay or a brief 1% trickle — at which point you've reinvented a small canary, which is fine and often the right hybrid); keep blue intact and drained until green survives one full traffic peak — blue *is* the rollback.

### 4. Deployment-order dependencies causing partial-rollout failures

- **Failure mode:** the release works only if everything in it lands together — service A's new API call reaches old service B; the app assumes a schema column the migration hasn't added on one shard; a shared-library wire-format change strands old consumers. Any progressive strategy (rolling, canary) *guarantees* mixed versions during the window, so "deploy A and B together" is not a plan, it's a race you'll eventually lose — and rollback recreates the same race backwards.
- **Detection:** review question on every cross-service or schema change: "does this work with every combination of old/new that the rollout window can produce?" Integration tests that run new-A against old-B (most test matrices only ever test new-against-new — that gap is exactly where this failure lives).
- **Fix/prevention:** the **expand/contract discipline**, mechanically: (1) *expand* — additive change ships first (new column nullable, new API endpoint added, new field optional), consumers untouched; (2) *migrate* — consumers move to the new shape, behind a flag if risky; (3) *contract* — remove the old shape only after every consumer is confirmed off it, releases later. Schema migrations are their own deploy step with their own rollback statement (a migration you can't reverse gets a written roll-*forward* plan *before* it runs, not during the incident). No hard release-ordering across services — if A must not precede B, that coupling is the defect to fix, not the runbook line to remember.

## The promotion spine (how this composes)

Same artifact digest through every stage: deploy to staging → automated smoke → progressive prod rollout (canary or rolling) gated on canary-vs-control analysis → full rollout → post-deploy verification against real metrics. Humans approve *promotions* where judgment is owed; machines execute the mechanics and the rollback. The full wiring is `devops-engineer/playbooks/build-a-delivery-pipeline-from-scratch.md`; when a rollout fails and nobody knows why, dispatch `devops-engineer/agents/deployment-failure-tracer.md`; once the system is unhealthy in ways beyond the rollout itself, that's an incident — `reliability-engineer/principles/incident-management.md`.
