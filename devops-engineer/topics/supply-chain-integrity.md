# Supply-Chain Integrity in the Pipeline — Extended Tier: Patterns & Pitfalls

**Applies to:** Sigstore/cosign 2.x, SLSA v1.0 vocabulary, Dependabot/Renovate-class bots, OCI registries (verified 2026) · **Last verified:** 2026-07-14

**Scope:** this doc owns supply-chain integrity *as a pipeline property* — what the delivery path pins, verifies, and refuses. Attacker tradecraft analysis, dependency-compromise incident response, and org security policy → `security-dev/`. The pipeline's angle is narrow and mechanical: **everything that influences a build is an input; every input is either pinned-and-verified or it's an open door.** Your delivery pipeline runs other people's code with your credentials — that sentence should organize everything below (and is why CI credential scoping, `devops-engineer/principles/secrets-in-delivery.md` failure mode 2, is inseparable from this doc).

## Production patterns

- **Inventory the inputs honestly.** For a typical service: language dependencies (and their transitive graph), base images, CI runner images, *CI plugins/actions* (a GitHub Action is arbitrary code in your pipeline — the most-forgotten entry on this list), Terraform providers/modules, Ansible collections, and every `curl | bash` in a setup script. If it's fetched, it's an input.
- **Pin everything to immutability, not to a name.** Lockfiles with integrity hashes enforced (`npm ci`, pip `--require-hashes`, `go.sum`); base images by digest; **third-party CI actions by commit SHA, never by tag** (`uses: some/action@v3` is a movable pointer whose owner is not you — the tag-repointing attack on popular actions is no longer hypothetical, it's documented history); Terraform providers via committed `.terraform.lock.hcl`.
- **Pinning without an update engine is rot.** The pin freezes known-good; the bot (Renovate/Dependabot-class) proposes moves as *reviewed PRs* with changelogs and diffs; CI validates; a human merges. Pinned-but-never-updated is how you're running the vulnerable version in June that was patched in January (`devops-engineer/principles/containers-and-orchestration.md`, failure mode 1). The pin and the bot are one pattern, not two options.
- **Internal artifacts: sign at build, verify at deploy.** The pipeline signs what it builds (cosign, keyless via the CI's OIDC identity) and attaches provenance (SLSA-style: which repo, which workflow, which commit built this). The deploy gate — admission policy (Kyverno/sigstore policy-controller-class) — refuses unsigned or wrong-identity images. This closes the "somebody pushed an image to the registry by hand" hole: the registry stops being a trust boundary you hope about and becomes one you enforce.
- **Proxy the outside.** A pull-through registry/artifact proxy (Artifactory/Nexus-class or cloud-native) gives you: availability when upstream is down, an audit log of what entered, a place to quarantine, and immunity to the *deleted/republished-upstream* trick (left-pad taught the availability half; every registry hijack since taught the integrity half).

## Common pitfalls

- **The transitive blind spot.** You reviewed your 40 direct dependencies; your lockfile contains 1,400. Nobody reviews 1,400 — that's what the layered mechanics are *for*: hashes catch substitution, the bot surfaces changes, scanners catch knowns. Accept that unknowns exist and scope credentials so a compromised dev-dependency in the *test* stage cannot reach prod credentials (stage isolation, `devops-engineer/principles/secrets-in-delivery.md`).
- **Install-time script execution.** `postinstall` scripts run at `npm install` — on the runner, with the runner's credentials, before any of your code executes. Registry-level malware overwhelmingly lives there. Mitigations that actually deploy: `--ignore-scripts` where the ecosystem tolerates it, install steps running with no secrets in scope, and network egress limits on build steps (a build that can't phone home can't exfiltrate).
- **The SBOM that nobody can query.** Generating SBOMs to satisfy a checkbox, storing them nowhere queryable — then a Log4Shell-class day arrives and "which services ship the bad version?" takes a week of grepping. The SBOM's value is *that query in minutes*; store per-release SBOMs indexed by service and version, and test the query before the fire drill does.
- **Verifying signatures nobody could fail.** A signing step without a *verification gate* is decoration; a verification policy that accepts any valid Sigstore signature (rather than *your CI's identity*) verifies only that someone, somewhere, signed something. The gate must pin issuer + identity.
- **The pipeline's own dependencies.** Runner images, setup scripts, shared workflow templates — infrastructure that builds the infrastructure, usually pinned by nobody. Apply the same rules one level down; a compromised shared workflow template is a skeleton key to every repo that imports it.
