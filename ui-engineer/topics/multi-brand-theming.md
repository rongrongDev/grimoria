# Multi-Brand & White-Label Theming — Production Patterns & Common Pitfalls

**Tier:** extended (patterns + pitfalls only). **Assumes:** the three-tier token architecture in `../principles/design-tokens.md` and the custom-property theming mechanics in `../principles/css-architecture.md` §theming — this doc is the delta for *N brands* instead of *N modes*. **Date:** 2026-07-13.

## The mental model in one paragraph

Dark mode reassigns semantic tokens; a **brand** reassigns semantic tokens *and* the raw palettes underneath them *and sometimes the rules themselves* (different type ramp, different radius language, different logo lockups, occasionally different component anatomy). The architecture question is where to draw the line between **theming** (data: token values per brand) and **forking** (code: brand-specific components), and the answer that survives is: push everything possible into data, hold the line on anatomy, and treat brand-specific *behavior* as a product feature with an owner — not a theme. The failure state of white-labeling is always the same: brand exceptions leak into component code as `if (brand === 'acme')`, and three years later you have N codebases wearing one repo.

## Production patterns

- **A brand is a token package.** Each brand ships raw palettes + semantic assignments + asset set (logos, illustration style, font files) as a build artifact from the same DTCG pipeline — brand × mode is a matrix (`acme-light`, `acme-dark`, …), generated, not hand-maintained. Semantic token *names* are identical across brands; only values differ. The moment a brand needs a semantic token others don't have, add it to the shared vocabulary with a sensible value for every brand — a per-brand vocabulary is the fork starting.
- **Brands may change values and scales, never anatomy through tokens.** Type ramp, spacing density, radius, shadows: all token-expressible, all fair game per brand. Component structure (what a Card contains, how a Dialog behaves) stays single-source. When a customer genuinely needs different anatomy, that's a **variant in the component's API** (`../principles/component-api.md`) available to all brands, or a paid product feature — never a brand-conditional in the component.
- **Delivery: static per-brand CSS for single-brand deployments** (each white-label deployment loads only its own token stylesheet — no runtime cost, no brand-flash) **or runtime scope-switching** (`[data-brand=…]`, for admin consoles showing multiple brands at once). Same tokens, two packagings; choose per deployment shape, don't build a bespoke runtime theming engine when 95% of white-label products serve one brand per origin.
- **The brand contract, written down:** what a new brand *must* provide (palette meeting the contrast pair-checks, two font weights, logo variants…), what it *may* override, what it *cannot touch*. Onboarding brand N+1 should be a fill-in-the-blanks exercise measured in days; if it requires a systems engineer making judgment calls per brand, the contract is missing and cost scales linearly forever.
- **Snapshot the matrix, sampled:** core component states × every brand in its default mode, full state coverage on the flagship brand, stress stories on the brand with the longest font metrics — per the sampling discipline in `../principles/visual-regression-testing.md` (the full cross-product is exactly the explosion that doc warns about). Every brand's money paths get the contrast pair-check in CI — customer-supplied palettes fail contrast *constantly*, and you want the build (not the audit, not the lawsuit) to say so; the contract above makes "your orange fails AA on white" a pre-agreed rejection, not a negotiation.

## Common pitfalls

1. **`if (brand === X)` in component code.** The first one is always "just this once for the launch." Grep for brand identifiers in component source; the count is your fork-in-progress metric and its trend belongs on the governance dashboard (`../principles/governance.md`). *Fix:* re-express as a token (if value-shaped), a variant (if anatomy-shaped), or a feature flag owned by product (if behavior-shaped).
2. **Brand-specific overrides stylesheets.** `acme-overrides.css` appended after the system styles — the specificity war (`../principles/css-architecture.md` §1) with a brand dimension, unthemed by future system changes and broken by every refactor. *Fix:* the override content is either missing tokens or missing variants; migrate it into the contract and delete the file.
3. **Fonts treated as interchangeable.** Brand B's typeface has a taller x-height and wider metrics; every layout tuned on Brand A clips or wraps. *Prevention:* line-height and spacing via tokens that ship *with the font choice* (the brand package includes its type ramp, not just a font-family swap); run the stress stories under the widest brand font; metric-compatible fallbacks per brand (`cross-browser.md` §fonts).
4. **The flagship-brand assumption.** All development and review happens on the house brand; customer brands rot — the dark-mode-happy-path failure (`../principles/css-architecture.md` §4) with a revenue attachment, since white-label customers are usually the paying ones. *Prevention:* CI snapshots per brand (above); rotate the "default local brand" across the team the way pitfall-1 in `cross-browser.md` rotates browsers.
5. **Unbounded brand-count math.** Every brand multiplies test surface, build time, and support. The contract keeps *marginal* cost near zero, but review the matrix budget when brand count crosses ~10: sampled snapshots, tiered support (flagship brands get full matrix, long-tail brands get contract-check + money-path), or the math eats CI.
6. **White-label ≠ unbranded.** Removing your brand isn't a theme with empty values — missing logo slots, "powered by" strings, hardcoded product names in components (grep for the product name in the component library; you'll be surprised). *Prevention:* brand assets and product-name strings are tokens/slots from day one.
