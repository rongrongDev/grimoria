# Voice & Conversational Interfaces — Production Patterns & Common Pitfalls

**Tier:** extended (patterns + pitfalls only). **Scope:** interaction patterns for voice and chat/LLM conversational interfaces — dialog design, error repair, confirmation strategy, testing method. LLM prompt construction itself is out of scope (see the sibling `prompt-engineer/` KB if present). **Validated against:** current-generation voice platforms and LLM chat interfaces; the dialog-design judgment predates and outlasts both. **Date:** 2026-07-13.

## The mental model in one paragraph

A conversational interface is a flow whose **states are invisible**. GUI users can *see* what's possible, where they are, and what the system understood; conversation users must carry all three in working memory, guided only by what the system says. So every hard problem in this file is a journey problem with the visibility removed: discoverability (what can I say?), grounding (did it understand me?), repair (how do I fix its misunderstanding?), and orientation (where am I in this task?). Design the conversation as a state machine with repair paths — exactly the `../principles/spec-handoff.md` matrix, where the rows are dialog states and the events are *the unbounded set of things humans say*, which is why the error/repair cells dominate the design instead of decorating it. The happy-path share of the work is even smaller here than in GUI: humans go off-script as the *normal case*.

## Production patterns

- **Prompts that shape the reply.** Users answer in the form the question suggests: "Do you want A or B?" gets parseable answers; "How can I help?" gets essays. In voice, end prompts with the question (people respond to the last thing they hear); offer at most ~3 options per turn (working memory, no screen). Discoverability is carried *in* the dialog — examples in the prompt ("you can say 'reschedule' or 'cancel'") at first use and after failures, dropped for practiced users.
- **Ground continuously, confirm proportionally.** Every turn signals what was understood (implicit confirmation: "Okay, Tuesday — what time?") so misunderstandings surface one turn late, not five. Explicit confirmation ("You want to cancel the 3pm with Dana — correct?") is reserved for costly/irreversible actions — the same stakes tree as `../principles/interaction-design.md` (reversible → act + undo; irreversible → confirm first). Confirming everything reads as robotic and trains users to say "yes" on autopilot, which defeats the one confirmation that mattered.
- **Escalating repair, never a loop.** The three-strike pattern: first miss → brief reprompt with the expected form ("Sorry — which day?"); second → reprompt with examples and options; third → *change strategy*: fall back to a different modality (screen list, keypad, buttons in chat), a human, or a graceful exit that preserves progress. The repair says what the system *needs*, never blames ("I didn't catch that" not "invalid input"), and never repeats the identical prompt — the user already answered that prompt in a way that failed; verbatim repetition is asking them to fail identically.
- **Support barge-in and shortcuts.** Experienced users know the menu — let them speak over prompts (barge-in) and compress multi-slot requests into one utterance ("reschedule tomorrow's 3pm to Friday morning" fills three slots at once — parse what's given, ask only for what's missing). Slot-filling that force-marches practiced users through one-question-per-turn is the voice equivalent of `journey-accessibility.md` §4's redundant entry.
- **Wizard of Oz before you build.** Conversation designs are testable with zero backend: a human operator plays the system (`../principles/prototyping-fidelity.md` decision tree §6) over a real audio channel or chat window. Ten sessions of WoZ reliably kill the three worst dialog assumptions for the cost of a script and an afternoon — and for voice, run it in *speech*, not text (pitfall 5).
- **For LLM-backed chat, the classic patterns tighten rather than relax:** ground by *showing* the interpretation before acting ("I'll draft an email to Dana canceling Tuesday — send it?"), gate tool-calls/irreversible actions behind explicit confirmation, and design the capability-question answer ("what can you do?") deliberately — model fluency makes users *over*-estimate capability, so ungrounded confidence is the failure mode, not stiffness.

## Common pitfalls

1. **Happy-path dialog design.** The flow diagram covers cooperative users answering in order; real transcripts are corrections ("no, *Friday*"), topic changes, compound answers, and silence. *Detection:* if the dialog spec has fewer repair states than task states, it's a demo script. *Prevention:* every prompt node answers: no-input, no-match, correction, "start over," and "help" — five columns, every row (the matrix again).
2. **No timeout/silence design (voice).** The system asks, the user hesitates — silence is ambiguous (thinking? gone? didn't hear?) and unhandled it becomes an error loop. *Prevention:* silence is an event with its own escalation (gentle reprompt → offer options → offer exit), distinct from no-match.
3. **The identical-reprompt loop.** "Sorry, I didn't understand" × 5, then hangup — the single most user-hostile pattern in voice, and it ships constantly because repair was left to the platform default. *Prevention:* the three-strike escalation above, spec'd per prompt node.
4. **Personality where clarity was needed.** Jokey error messages ("Whoops! My bad! 🙈") on repeated failures read as mockery by the third occurrence; charm has negative marginal utility in repair states. Persona belongs in greetings and success; repair states get short, concrete, form-guiding language.
5. **Testing voice in text.** The team reads the dialog script and nods; spoken aloud, the prompt is 14 seconds long, the options are unmemorable, and the TTS mangles the product name. Text hides prosody, length, and memory load. *Prevention:* voice designs are evaluated by *listening and speaking* — WoZ over audio, prompts read by the actual TTS.
6. **Ignoring the transcript goldmine.** Live conversational products log every misunderstanding verbatim — the richest free research corpus this KB knows of (`../principles/information-architecture.md`'s search-log mining, but for entire dialogs) — and most teams never mine no-match utterances for missing intents and vocabulary. *Prevention:* scheduled transcript reviews; top no-match clusters become new intents or better prompts.
