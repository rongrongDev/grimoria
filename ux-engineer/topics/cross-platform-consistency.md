# Cross-Platform Interaction Consistency — Production Patterns & Common Pitfalls

**Tier:** extended (patterns + pitfalls only). **Scope:** keeping one product's *interaction behavior* coherent across web, iOS, Android, and desktop. Visual/theming parity across platforms is `ui-engineer/`'s (tokens travel; see `ui-engineer/topics/multi-brand-theming.md` for the mechanics). **Validated against:** iOS HIG / Material 3 / current web conventions — the *judgment* here is which layer follows which rulebook, and that's stable. **Date:** 2026-07-13.

## The mental model in one paragraph

Users don't want your platforms to be *identical* — they want them to be **predictable**, and predictability has two sources that conflict: consistency with *your product* on other platforms, and consistency with *the platform* they're holding. The resolution is a layering rule: **the platform owns the mechanics, the product owns the model.** Mechanics — navigation gestures, back behavior, dialogs, pickers, share sheets, keyboard shortcuts — follow the platform's conventions, because users spend far more hours in the platform than in your product and their muscle memory is not yours to retrain. The model — what things are called, how the flow is sequenced, what states exist, what an action does, what's confirmable vs. undoable — is the product's, and must be identical everywhere, because *that's* what users carry between devices. Almost every cross-platform fight dissolves once you name which layer the disputed thing lives in.

## Production patterns

- **One behavioral spec, per-platform mechanics annexes.** The state × event matrix (`../principles/spec-handoff.md`) is written **once per flow** — states, transitions, feedback semantics, terminology, focus/announcement intent — and is platform-neutral. Each platform then gets a short annex mapping mechanics: "confirm-destructive" → action sheet (iOS) / dialog (Android/Material) / inline confirm (web); "back" → edge swipe + nav bar (iOS) / system back — which must work (Android) / browser back — which must work (web). The annex maps *named patterns*, so the matrix never forks.
- **A parity matrix as a living artifact.** Rows = capabilities and behaviors (operations, edge-state handling, terminology, a11y task-completion); columns = platforms; cells = same / intentionally different (with the layering rationale) / *unintentionally* different (a bug) / missing. Review it per release. Without the artifact, parity is folklore, and drift is discovered by the users who switch devices — who are disproportionately your heaviest users.
- **Terminology and model are non-negotiable across platforms.** The same operation has the same name, the same consequences, and the same stakes-treatment (undoable here = undoable there) on every platform (`../principles/journey-accessibility.md` §4's one-verb rule, widened). If archiving is reversible on web and permanent on mobile, that's not a platform adaptation — it's a trap (the `spec-handoff.md` war story was exactly this class of failure).
- **Input parity per platform's full input set.** Web and desktop: complete keyboard paths (`../principles/journey-accessibility.md`); iPadOS/desktop-class tablets: pointer + keyboard, not just touch; Android/iOS: TalkBack/VoiceOver task-completion respectively; touch-capable laptops exist — hover can never be the *only* path anywhere (`../principles/interaction-design.md` §4 owns the rule; this file's addition is that the parity matrix has an input row per platform).
- **Test the cross-device *journey*, not just each platform.** Start a task on the phone, finish on the web — the handoff (state sync, drafts, notifications deep-linking to the right screen in the right state) is a journey no per-platform QA plan covers, and it's where the model layer's consistency actually gets cashed in.

## Common pitfalls

1. **Web patterns ported to mobile wholesale.** Hover-revealed actions (no hover exists), tiny link-styled tap targets, dialogs where a sheet is conventional, "click here" copy. *Detection:* the mobile app feels like a website in a trench coat; row one of the parity matrix's input section is red. *Prevention:* the mechanics annex is written by someone fluent in that platform's HIG/Material conventions, not translated from the web spec.
2. **Lowest-common-denominator design.** To keep platforms "consistent," every platform gets the subset all of them can do identically — no swipe actions (web can't), no keyboard shortcuts (mobile can't), no drag-and-drop. Uniformly mediocre is a *choice*, and it's the wrong reading of consistency: the model is what must match, and each platform should exploit its native strengths *as alternate mechanics for the same model operations* (swipe-to-archive and `E`-to-archive are the same cell of the same matrix).
3. **Platform teams drifting apart silently.** Independent teams, independent backlogs, and eighteen months later the same feature has three information architectures and two names. *Detection:* the parity matrix audit — the first one ever run at an org is always a massacre. *Prevention:* the shared behavioral spec is the source of truth and changes to it are cross-team events; the annexes are where autonomy lives.
4. **Breaking the platform's back button.** Android system back that exits the app from three levels deep, web back that loses a half-completed form or traps the user (history hijacking), iOS edge-swipe disabled by a custom gesture. Back is the single most-used navigation mechanic on every platform; breaking it is the fastest way to make an app feel foreign *and* fail accessibility. *Prevention:* back behavior is a mandatory row per flow in the annex — where does back go from every state, and what survives it (`../principles/spec-handoff.md`'s "revisited" state, per platform).
5. **"Consistent" branding overriding platform a11y conventions.** Custom controls everywhere for visual sameness → each platform's AT users get a worse-than-native experience simultaneously (custom pickers that VoiceOver reads as buttons, web selects rebuilt without keyboard support). Native/platform controls carry years of AT integration for free; the burden of proof is always on the custom control (`ui-engineer/principles/component-accessibility.md` for the construction cost being taken on).
6. **Parity treated as a launch checklist instead of a maintenance property.** Platforms are aligned at the feature's launch, then per-platform fixes accrete and no one re-checks. *Prevention:* the parity matrix reviewed on a cadence, and any "intentionally different" cell carries its rationale inline so the next reviewer can tell deliberate adaptation from rot.
